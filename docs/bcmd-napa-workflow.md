# BCMD → NAPA → Payroll workflow (MVP contract, 2026-11-03)

Source of requirements: the 2026-11-03 review meeting fix list
(vault `20-Projects/TULOY/meetings/2026-11-03-bcmd-napa-payroll-review.md`),
"Proposed ESSI 4Ps Data Quality Parameters" (Ma'am Carla, draft), the
TULOY MySQL batch runbook v1 (§4–§6) and the NAPA template workbook
(`NAPA_V2_RAW_DETAILED`, `NAPA_V2_SUMMARY` as edited live in the meeting).

All routes are under `/v1/api/tuloy/staff/bcmd`. Nothing here records or
releases a payment.

## Workflow

1. **BCMD Criteria Batching** — choose a category; its fixed (non-negotiable)
   rules apply automatically; optional filters narrow the list; save a frozen
   batch with a generated, unique name.
2. **DQA in BCMD** (separate, background, versioned). Progress: status,
   processed, total, passed, failed, excluded, percent. Staff see two outcomes,
   Passed or Failed, and every failed record shows its remark (a REVIEW finding
   is shown as Failed). Findings and duplicate-selection review are in the BCMD
   DQA window; a decision needs a fresh run.
3. **Automatic availability** — as soon as the batch's latest DQA run is
   completed on the current ruleset, with no duplicate-selection decision after
   it, the batch is in NAPA and in the Payroll batch list. There is no approval
   and no manual handoff step (both removed 2026-11-05).
4. **NAPA** — a file register only (no batch creation, DQA or review there): each
   available batch with NAPA Detailed and NAPA Summary (passed records) and NAPA
   Failed (failed records with their remarks).
5. **Payroll** — eligible records only: PASS in the latest usable DQA run, with no
   recorded payment that blocks them now.

## Categories (fixed rules)

Every category also requires `vw_verify_member_bene`: active 4Ps client
status (CS 1, 3, 14, 15, 19, 28) and eligible grade level, plus age 18–30
inclusive on today's **Manila** date. The API computes the bounds in Python
(`date_of_birth > today − 31 years AND date_of_birth <= today − 18 years`;
29 February maps to 28 February) and passes them as parameters, because the
database session time zone is UTC and `CURDATE()` would be a day early before
08:00 Manila time. DQA rechecks the age on the run date (`AGE_OUTSIDE_RANGE`).

| Code | Label | Prefix | Fixed rules | Optional filters |
|---|---|---|---|---|
| TK | Tuloy Kolehiyo | `TLY-KLHYO` | ENROLLED, year level 1, semester 1 | academic year |
| TA | Tuloy Aral | `TLY-ARL` | ENROLLED | academic year, semester, year level |
| TT | Tuloy Trabaho | `TLY-TRBH` | GRADUATED | academic year |

Every category reads the unified source (below) and excludes any record that a
recorded payment blocks for that category and period ("Payment history").

`academic_year` must be `YYYY-YYYY` with consecutive years (e.g. `2026-2027`);
anything else is 422. `semester` (1–3) and `year_level` (1–6) are accepted for
TA only; sending them for TK or TT is 422 rather than silently ignored.
TT graduates may have no semester; it is stored as 0.

## Unified sources (CHED and TESDA)

Candidates and batch save read the same source as `/GetUnifiedMatchedBene` and
`vw_unified_matched_enrollment`: CHED degree records (`enroll_matched_CHED_tbl`),
plus TESDA diploma records (`enroll_matched_TESDA_tbl.diploma`) **only when that
`tuloy_id` has no CHED match**. The view has no stable row identity, so
`bcmd_candidates.py` reads its two source tables directly, the way COR review
does. Each record is identified by `source_ref`: `CHED:<id>:degree` or
`TESDA:<id>:diploma`, so the two sources' row IDs never collide. The claim key
is unchanged: member, academic year and semester (0 when absent).

TESDA diploma fields map as: `academic_year`, `semester` (digits only, else
none), `year_level`, `enrollment_status` (trimmed, upper case), `program_name`.
They are used only when present; no period is derived or invented.

TESDA short courses (`short_course` only) have no academic year, semester or
year level (Q-P1, Q-P3). They are never selectable in any category and are
counted separately as `short_course_excluded_count`. DQA would hold one as
`SHORT_COURSE_POLICY_PENDING` (REVIEW), or `SHORT_COURSE_NOT_ELIGIBLE_TA`
(FAIL) in TA.

Each frozen member keeps its own `source_agency` (CHED or TESDA) and
`course_type` (degree or diploma). A batch's `source_agency` is CHED, TESDA or
MIXED; the NAPA DETAIL and SUMMARY use each member's own source. CHED-only
batches produce the same bytes as before. TESDA payroll rates and any TESDA
eligibility not listed here are not decided: no rate or rule is invented
(open question Q-T1).

Batch names are generated by the web client as `<prefix>-YYYYMMDD-HHMMSS-mmm`
(e.g. `TLY-KLHYO-20261103-181058-001`) and are read-only on screen. The API
only enforces uniqueness, so the exact format can change without an API release
(open question Q3).

## Routes

### `GET /status`
`{available, categories: ["TK","TA","TT"], category_options: [{code, label,
name_prefix, optional_filters, rules: [{key, label}]}], max_records: null,
creation_available, dqa_runs_available, export_available, blocking_approvals: [] (always
empty since 2026-11-05; kept for older clients),
export_file_types: ["DETAIL","SUMMARY","FAILED"], reason}`.
The web shows `rules` as read-only "Fixed rules" chips and offers only
`optional_filters` as inputs. `max_records` is null: there is no fixed batch
size, only the number of eligible records.

### `GET /candidates`
Query: `category` (TK default), `limit` 1–200 (page size only, never a batch
size), `offset` 0–10,000,000, `academic_year`, `semester` (TA only),
`year_level` (TA only), `program_name`, `region_name`, `search`.

Response: `{items: [{source_ref, source_agency, course_type, source_record_id,
tuloy_id, academic_year, semester, year_level, enrollment_status,
program_name}], has_more, total_count, total_status, count_unit,
payment_excluded_count, short_course_excluded_count, limit, offset, category,
criteria, rules: [{key, label}]}`. Rows come in stable order: CHED, then TESDA,
each by source row ID.

- `total_count` is the **exact** number of eligible records; it is never capped.
  If it cannot be counted within 5 seconds it is `null` with `total_status`
  `UNAVAILABLE` (otherwise `EXACT`).
- `count_unit` is `ENROLLMENT_RECORD`: counts are of source enrollment records,
  not people.
- `payment_excluded_count`: records that match every other rule but a recorded
  payment blocks. No beneficiary data is returned for them.
- `short_course_excluded_count`: TESDA short courses in scope by beneficiary,
  age, region and search (they have no period to filter on).
- 503 `PAYMENT_HISTORY_UNAVAILABLE` when payment history cannot be read.

### `POST /batches` (Idempotency-Key)
`{name, category: "TK"|"TA"|"TT", record_refs: ["CHED:1:degree", "TESDA:7:diploma", ..]}`,
`{name, category, record_ids: [..]}` (CHED source row IDs, for earlier clients) or
`{name, category, criteria, record_count}`. There is no fixed batch size. A
`record_count` above the number of eligible records returns **422
`RECORD_COUNT_EXCEEDS_ELIGIBLE`** ("Only N eligible records match; M were
requested") and saves nothing. Criteria select the first `record_count` records
in the candidate order, with the same filters and payment-history check as the
preview, inside the save transaction. An explicitly selected record that is no
longer eligible, including one that a payment recorded since now blocks,
returns **422 `SOURCE_NOT_ELIGIBLE`** and saves nothing. A criteria save stores
`payment_excluded_count` (the matching records payment history excluded at
save; `null` for explicit selections or when the count did not finish in time). A name that already exists
(case-insensitive) returns **409 `BATCH_NAME_EXISTS`**; the database also has a
unique index on the name (migration 0020). The same Idempotency-Key with the
same body replays the original batch; with a different body it is 409
`IDEMPOTENCY_CONFLICT`. A concurrent save with the same key returns 409
`BATCH_CONFLICT`: retry the same key to get the replay. On `BATCH_NAME_EXISTS`
the web regenerates the name and retries with a new key. A replay returns the
batch as saved, with `export_ready` false, `dqa_run_status` `NOT_RUN` and
`latest_dqa` null even if runs or exports exist since; read `GET /batches/{id}`
for the current state.

### Batch object (list, detail, create)
`{public_id, name, category, source_agency (CHED|TESDA|MIXED), status, member_count,
payment_excluded_count, created_at,
dqa_outcome, dqa_block_count, dqa_warn_count, export_seq, export_ready,
dqa_run_status, latest_dqa, dqa_refresh_required, napa_handoff}` where `dqa_run_status` is
`NOT_RUN|QUEUED|RUNNING|RETRYING|FAILED|COMPLETED` and `latest_dqa` is `null`
or `{public_id, run_no, status, total, processed, passed, failed, review_count,
percent, completed_at, ruleset_version, ruleset_current}`. `dqa_outcome` is the legacy save-time snapshot check
and is not the DQA result. `napa_handoff` is `{status: VALID|STALE|NOT_RECORDED,
reasons, current: null | {public_id, dqa_run_id, dqa_run_no, passed_count,
actor_agency, created_at}}`.

`GET /batches?register=napa` is the NAPA file register: batches with a recorded
handoff (VALID, or STALE with its reason), plus earlier batches that already have
issued files (`NOT_RECORDED`, so those files stay downloadable). It is filtered in
the query, before `limit`/`offset`. Each register item also has `napa_files`, the
same per-file object as export readiness, so the register makes no request per row.

### NAPA availability (automatic)
A batch is available in NAPA and Payroll as soon as its latest DQA run is
COMPLETED on the current ruleset and no duplicate-selection decision came after
it. Nothing has to be approved or recorded first. A run with no PASS record is
available too, so its FAILED file (remarks for correction) can be issued.
`GET /batches/{id}/napa-handoff` reports it as `{batch_id, status, reasons,
current, history, automatic: true}`: `VALID` (available), `STALE` with the DQA
reason (`DQA_IN_PROGRESS`, `DQA_FAILED`, `DQA_RULESET_OUTDATED`,
`DQA_REFRESH_REQUIRED` or `BATCH_PURGED`), or `NOT_RECORDED` (no DQA run yet).
`POST /batches/{id}/napa-handoff` is kept only for older clients: it records an
audit row with its earlier checks, but nothing requires it and the web no longer
calls it.

Files already issued are never changed or removed and stay downloadable. DQA
still cannot be run again on a batch that has files (`DQA_BATCH_EXPORTED`).

### DQA runs
`POST /batches/{id}/dqa-runs`, `GET /batches/{id}/dqa-runs`,
`GET /batches/{id}/dqa-runs/{run}`, `GET /batches/{id}/dqa-runs/{run}/results`.
Result items: `{line_no, member_ref, hhid, last_name, first_name, outcome:
PASS|FAIL|REVIEW, findings: [{rule_code, severity, remark, field}]}`.
The run object also has `checks` (what this ruleset evaluates) and
`not_evaluated` (parameters it cannot evaluate from TULOY data), plus
`ruleset_version` and `ruleset_current`. Results accept `?outcome=PASS|FAIL|REVIEW`.
A new run on a batch that already has a NAPA export is refused with 409
`DQA_BATCH_EXPORTED`: the exported files must keep matching their run. Use a
new batch instead.

### `GET /batches/{id}/export-readiness`
```
{batch_id, ready, blocking_reasons,            # DETAIL, kept for older clients
 dqa_run: null | {public_id, run_no, status, total, passed, failed, review_count},
 files: {DETAIL: {ready, blocking_reasons, row_count, member_count, data_rows, export_no},
         SUMMARY: {...}, FAILED: {...}},
 napa_handoff: {status, reasons, current},
 exports: [<export object, see below>]}
```
`member_count` (and `row_count`, its earlier name) is the number of member
records a file covers; `data_rows` is the number of CSV rows after the header.
For DETAIL and FAILED they are equal; the SUMMARY has one row per barangay plus
the TOTAL row, so its `data_rows` is not a member count. Example: 201 members,
1 PASS and 200 REVIEW give DETAIL 1 member (1 row), SUMMARY 1 member (2 rows)
and FAILED 200 members (200 rows).
A file type that already has a completed export from the latest run reports
`ready: true` with that `export_no` (re-download).
Reason codes: `DQA_NOT_RUN`, `DQA_IN_PROGRESS`, `DQA_FAILED`,
`DQA_RULESET_OUTDATED`, `DQA_REFRESH_REQUIRED`, `BATCH_PURGED`,
`NO_PASSED_RECORDS`, `NO_FAILED_RECORDS`, `VERSION_UNSUPPORTED`.

### `POST /batches/{id}/exports` (Idempotency-Key)
Body `{file_type: "DETAIL"|"SUMMARY"|"FAILED"}`. Uses the batch's latest DQA
run, which must be COMPLETED on the current ruleset: a newer queued, running or
failed run blocks exports (and the payroll preview) even if an older run
completed. If that run already has a completed export of the same type, the existing
export is returned (immutable re-download), not a new version. Response:
`{batch_id, export_no, file_type, status, sha256, byte_count, row_count,
dqa_run_id, dqa_run_no, filename, download_url}`.

Every file type needs the batch to be available (above). Before a new file is
built, every PASS record of the run is checked
against payment history again; if a payment recorded since DQA now blocks one,
nothing is exported and the response is 409 `PAYMENT_HISTORY_CHANGED` (the
population of a file is never changed silently; issued files are not touched).
Errors (409): `NAPA_DQA_REQUIRED` (no completed run on the current ruleset),
`PAYMENT_HISTORY_CHANGED`, `NAPA_NO_RECORDS` (the file would be empty: no
passed records for DETAIL/SUMMARY, no failed records for FAILED),
`NAPA_VERSION_UNSUPPORTED`, `NAPA_BATCH_BLOCKED` (the frozen batch or the stored
DQA results are inconsistent, or a passed record fails export validation; also on
download; use a new batch), and `IDEMPOTENCY_CONFLICT` (key reused for another
file type). An unknown `file_type` is 422. Exports made before DQA runs existed
(no `dqa_run_id`) still download unchanged.

### `GET /batches/{id}/exports/{no}/download`
CSV. File names: `NAPA-DETAILED-<batch name>.csv`, `NAPA-V2-SUMMARY-<batch name>.csv`,
`NAPA-FAILED-<batch name>.csv`.

- **DETAIL** — the 20 `NAPA_V2_RAW_DETAILED` headers, passed records only,
  renumbered in line order.
- **SUMMARY** — the 18 `NAPA_V2_SUMMARY` headers as edited in the meeting
  (CATEGORY removed): grouped by region, province, municipality and barangay
  (name + PSGC); Household Count, Family Count (nulls excluded), Member Count,
  Sex M/F Count (`M <n> / F <n>`), IP Count (IP = YES), validated source,
  TK, TA, TT and Total; last row `TOTAL`. Passed records only.
  The validated-source column lists `<SOURCE> <n>` for each source present,
  in the order CHED, TESDA, joined with ` / ` (for example `CHED 12`, or
  `CHED 12 / TESDA 3`). A batch has one source agency today, so one term
  appears (open question Q6: the template cell had no agreed format).
- **FAILED** — failed records with remarks for correction.
  16 headers (`docs/templates/napa-failed-headers.csv`): LINE NO., REGION,
  PROVINCE, MUNICIPALITY, BARANGAY, HHID, MemberID, MEMBER Last/First/Middle
  name, Ext. name, Academic Year, Semester, DQA RESULT (`FAILED`; files issued
  as failed-v1 also used `FOR VERIFICATION` and still download unchanged), RULE CODES (`; `-separated), REMARKS (`|`-separated).
  LINE NO. is the member's line in the batch, so it matches the DQA results.

Formula guard: DETAIL (machine-read by NAPA) refuses a value starting with
`=`, `+`, `-`, `@`, tab or carriage return, including full-width forms; DQA
fails such a record (`NAPA_FIELD_INVALID`), so it never reaches DETAIL.
SUMMARY and FAILED (read by people) prefix such a value with an apostrophe and
replace line breaks with spaces, so the record can still be listed for
correction.

Files are not stored. Each download rebuilds the bytes from the frozen batch
and the stored DQA results and checks them against the hashes and counts saved
at export time. Any change that alters a file's bytes for the same data
(headers, columns, formatting) therefore needs a new serialization version, and
the old builder must be kept so files already issued keep downloading. A file
made under an older ruleset stays downloadable.

### `GET /batches/{id}/payroll-preview?months=1..12`
Read-only estimate from the eligible records: PASS in the latest completed,
current, not invalidated DQA run, with no recorded payment that blocks them now
(`422 NAPA_DQA_REQUIRED` when there is no such run). Same response as before
plus `category`, `dqa_run_id`, `dqa_run_no`, `payment_blocked_count`,
`payment_findings` and `source`. The rate follows each member's own source
track; TA/TT and TESDA rates are not yet confirmed. The web shows it on the
Payroll page only; NAPA no longer has a payroll preview.

## Payment history

One module, `bcmd_payment_history.py`, decides whether a recorded payment blocks
a record. Candidates, counts, batch save, DQA, NAPA handoff, new NAPA files and
every payroll path (listing, compute, exports, generation) call it.

Source: `payment_transaction` only (the payments module's table; the only
payment source evidenced in this repository). A payment is matched to the
member by `member_id`; its category comes from its batch (`batch_id` →
`bcmd_batch.category`), and its period from that batch's member row. A TA
payment whose batch has no single period for the member is unmapped.
Disbursements recorded anywhere else are not seen (`EXTERNAL_DISBURSEMENT_LEDGER`
stays "not evaluated").

| Recorded payment | Blocks |
|---|---|
| TK | TK only, any period |
| TT | TT and TA; never TK |
| TA | TA for the same academic year and semester only |
| Short course | Never TA; other short-course eligibility is pending (Q-P1) |
| Unmapped, not void | Every category (`PAYMENT_UNMAPPED`, Q-P4) |
| Void | Nothing |

Statuses: the confirmed-paid and void status sets are **empty** until officially
confirmed (Q-P2). Every recorded payment is therefore pending: it blocks, but is
never called paid. Screens show "Payment recorded, not yet confirmed paid."
This includes the payments a batch's own payroll generation records: after
generation those members are no longer payable from any batch (Q-P6).

Finding codes (DQA results, payroll `payment_findings`; each carries
`payment_ref` = `payment_transaction:<internal row id>` in DQA results; the FAILED
file keeps its approved columns, so it shows the code and remark only):

| Code | Severity | Meaning |
|---|---|---|
| `ALREADY_PAID_TK` | FAIL | A confirmed TK payment is recorded (TK is paid once) |
| `ALREADY_PAID_TT` | FAIL | A confirmed TT payment is recorded (TT is paid once) |
| `TA_BLOCKED_BY_TT_PAYMENT` | FAIL | A confirmed TT payment ends TA |
| `ALREADY_PAID_SAME_PERIOD` | FAIL | A confirmed TA payment for the same academic year and semester |
| `SHORT_COURSE_NOT_ELIGIBLE_TA` | FAIL | A TESDA short course is never TA |
| `PAYMENT_PENDING` | REVIEW | Payment recorded, not yet confirmed paid |
| `PAYMENT_UNMAPPED` | REVIEW | A recorded payment has no category or period |
| `SHORT_COURSE_POLICY_PENDING` | REVIEW | TESDA short-course eligibility is not decided |

Fail closed: if payment history cannot be read (missing table, column or
SELECT grant), candidates, save, handoff, payroll and generation return **503
`PAYMENT_HISTORY_UNAVAILABLE`** and do nothing; a DQA run retries and then
fails, so no unchecked record passes. The BCMD readiness check requires SELECT
on `payment_transaction` for the BCMD account.

Payment generation (`routers/payments.py`) is serialized per beneficiary: inside
its term lock and a READ COMMITTED transaction it takes one row lock per member
in `bcmd_payment_member_lock` (SHA-256 key, sorted order), then re-reads payment
history. A second generation in another term or assistance type waits, then sees
the first payment and skips that member. Each skipped member is recorded in
`bcmd_payment_exclusion` with the reason code, line number and payment row
reference only.

## DQA ruleset `essi-mvp-v4`

v4 adds the payment-history findings above (parameter 13) and the TESDA
short-course holds; runs on `essi-mvp-v3` are outdated and need a fresh run.

FAIL: missing member ID / HHID / name; duplicate member in the batch; invalid
or missing birth date; age outside 18–30 on the run date; incomplete or invalid
academic period (TK/TA); invalid NAPA field; legacy snapshot mapping issue;
the same member and period already in another batch with a NAPA export
(duplicate claim, parameters 12–13); a confirmed-paid payment that blocks the
category and period; a TESDA short course in TA.

REVIEW (shown to staff as Failed, with its remark): the same member and period selected in another
batch that has no NAPA export yet; a recorded payment not yet confirmed paid, or
one that cannot be mapped; a TESDA short course while its policy is pending.

EXCLUDED: a duplicate-selection review kept the same member and period in another
batch. It is in no NAPA file (docs/bcmd-duplicate-selection-review.md).

Checked at selection by the source view and recorded in the ruleset: client
status (parameter 04), partner validation / enrollment / graduation (07, 11, 14).

Not evaluated (disclosed on screen and in the ruleset): SHS status (05),
pathway (06), TVET program (09), Tuloy Gabay (10), external ESSI disbursement
ledger (13, beyond TULOY's own NAPA exports), payment account (15, Payroll).

Duplicate claims are matched on member, academic year and semester regardless
of category, so the same member cannot be claimed under TK and TA for the same
period (to confirm with the BCMD owner). Only a DETAIL export counts as a claim.

Known limit: purging a batch clears its member references, so a purged batch's
NAPA export no longer counts as a prior claim.

Two unexported batches that select the same member and period both hold that
member as REVIEW (`SELECTED_IN_OTHER_BATCH`, shown as Failed with its remark).
Neither can pass it until one of the batches is exported or purged, or a
duplicate-selection decision keeps it in one batch. After an export, a new run of
the other batch fails the member as a duplicate claim only if the exported
DETAIL included it (it passed there); if it was held there it was never claimed,
and the other batch can pass it.

## Release

There are no export approvals: the five approval gates were removed on
2026-11-05, so nothing has to be recorded before NAPA files can be made, and a
code or document change never blocks exports. `python -m
scripts.napa_export_approvals` still prints the content hashes for reference
only.

Migrations (DBA review, apply in order, rollbacks in `migrations/rollback/`).
For staging, guarded DbGate files for 0018–0022 are in `docs/schema/dbgate-apply/`
(see its README):

- `0020_bcmd_batch_name_unique` — renames existing duplicate names by appending
  ` #<id>` to every copy after the first, then adds `uq_bcmd_batch_name`.
- `0021_bcmd_export_file_types` — `bcmd_batch_export.dqa_run_id` (nullable FK to
  `bcmd_dqa_run`), unique `(dqa_run_id, file_type)`, file type check widened to
  DETAIL/SUMMARY/FAILED. The rollback refuses while any export made from a DQA
  run exists (SUMMARY, FAILED, or a DETAIL with `dqa_run_id`).
- `0022_bcmd_member_claim_index` — `ix_bcmd_member_claim (member_ref,
  academic_year, semester)` for the cross-batch claim check.
- `0024_bcmd_payment_history` — `bcmd_payment_member_lock` (one row per
  beneficiary digest, the generation lock) and `bcmd_payment_exclusion` (the
  generation's skipped members: reason code, line number, payment row reference).
  BCMD-owned; `payment_transaction` is not altered.
- `0025_bcmd_unified_sources` — per-member `source_agency` / `course_type`
  (defaults CHED / degree, so existing members are unchanged), unique source per
  batch, batch `source_agency` CHED|TESDA|MIXED, nullable
  `payment_excluded_count`. The rollback refuses while TESDA or MIXED data exists.
- `0026_bcmd_napa_handoff` — `bcmd_napa_handoff` (one row per handed-off run:
  batch, run, claim epoch, PASS count, actor reference and agency, request ID,
  idempotency key and request hash; never updated or deleted) and the
  `NAPA_HANDOFF_RECORDED` audit event. The API no longer needs a handoff row
  (availability is automatic); the table keeps rows recorded by older clients.
  The rollback stops at its first statement once any handoff has been
  recorded (its audit events fail the restored check), so recorded handoffs are never dropped.
- `0027_bcmd_lookup_tables` — `lib_sex`, `lib_ext_name` and `lib_ip_group` in the
  application database: the sex, name extension and IP group lookups of the batch
  source query, so the API reads nothing outside its own database. Same ids, names,
  codes and flags as consultant_ods `lib_sex_v3`, `lib_ext_name_v3` and
  `lib_ip_group_v3` (PPIS audit columns not kept). Additive; the rollback drops the
  three tables. After the guarded 0027 step reports VERIFIED, run
  `docs/schema/bcmd_lookup_copy.sql` once in Workbench (dswd_4ps_tuloy_dev as default
  schema) and expect `copy_status` COPIED. It only adds and refreshes rows, never
  deletes; re-run it after the PPIS libraries change. BCMD readiness fails with
  `reference_data` / `empty_lookup` while any of the three is empty. The API needs
  SELECT on the three tables (a schema-level grant on dswd_4ps_tuloy_dev covers
  them) and no right in consultant_ods.

web last. A batch whose latest run used an older ruleset needs a fresh DQA run
before new files; issued files stay downloadable. To go back, roll back the API first, then the database. Apply 0020 with
batch creation paused: its rename is committed before the index is added, so a
duplicate inserted in between makes the index step fail (re-running is safe).
The 0021 rollback refuses while any run-based export exists.

The DQA worker (`python -m scripts.bcmd_dqa_worker`) must run in every
environment; without it runs stay QUEUED and nothing can be exported. Nothing in
this repository's CI deploy (`update-tuloy.sh api`) starts it, so on a host the
worker runs as its own service: see `docs/deploy/tuloy-bcmd-dqa-worker.service` (a
systemd template; the host administrator fills in the API's user, directory and
virtualenv, and restarts the worker after each deploy).

## Open policy questions

behavior shown until it is decided.
